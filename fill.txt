# Deploy and Host Reminder on Railway

Reminder is a Telegram bot that turns plain language into scheduled reminders. Type "remind me tomorrow 5pm buy milk" and it parses the time, or use a guided wizard. Users get a private dashboard and inline mode for setting reminders from any chat, with recurring schedules and early alerts. Postgres keeps everything across restarts.

## About Hosting Reminder

Deploying the template creates two Railway services: a Node.js bot service and a PostgreSQL database with a persistent volume. The bot builds with RAILPACK, starts with `node index.js`, and listens on Railway's injected `PORT`. It exposes `POST /webhook` for Telegram updates and a `/health` endpoint that pings the database. The database is private by default and reachable only over Railway's private network, so `DATABASE_URL` is wired to the bot automatically. You supply one secret: `TELEGRAM_BOT_TOKEN` from @BotFather. After the first deploy, enable public networking and point the bot's webhook at `https://<your-domain>/webhook`. Each push to the connected repo redeploys the service.

## Common Use Cases

- Personal reminders in DM — natural-language scheduling plus daily, weekly, monthly, and yearly recurring reminders with a pre-alert nudge
- Shared reminders for a group or channel — inline mode lets anyone in a chat set a reminder without adding the bot to the group
- A shared reminder server for a family or team — one timezone-aware dashboard, one calendar view, and every reminder persisted in Postgres

## Dependencies for Reminder Hosting

- A Telegram bot token from [@BotFather](https://t.me/BotFather) — the only value you need to provide (`TELEGRAM_BOT_TOKEN`)
- A PostgreSQL database — bundled in the template with a Railway volume attached at `/var/lib/postgresql/data` for persistent storage
- A public domain for the bot service, so Telegram can deliver updates to `POST /webhook`, and outbound access to `api.telegram.org` for sending messages

### Implementation Details

Variables the template wires up:

```bash
# Bot service
DATABASE_URL="${{Postgres.DATABASE_URL}}"   # private-network connection string
TELEGRAM_BOT_TOKEN=""                       # from @BotFather

# Postgres service
POSTGRES_USER=""                             # superuser role, defaults to "postgres"
POSTGRES_DB=""                              # database name, defaults to POSTGRES_USER
POSTGRES_PASSWORD="${{ secret(32, ...) }}"  # random 32-char password at deploy time
DATABASE_URL="postgresql://${{PGUSER}}:${{POSTGRES_PASSWORD}}@${{RAILWAY_PRIVATE_DOMAIN}}:5432/${{PGDATABASE}}"
SSL_CERT_DAYS=""                            # TLS cert lifetime, defaults to 820 days
```

Point the bot at your deployed domain once it is live:

```bash
curl -X POST "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" \
  -d url="https://<your-domain>/webhook" \
  -d secret_token="$WEBHOOK_SECRET"
```

Set `WEBHOOK_SECRET` on the bot service to have Telegram sign requests; the app rejects any request whose `x-telegram-bot-api-secret-token` header does not match, and warns at startup if the variable is missing.

Other implementation notes:

- The schema is created on startup with idempotent `CREATE TABLE IF NOT EXISTS` (`user_settings` for timezone and UI state, `reminders` for the schedule), so there is no migration step to run.
- A background poll on the `reminders` table fires due reminders and early alerts, and rolls recurring ones forward; `FOR UPDATE OF r SKIP LOCKED` keeps it safe if more than one instance runs.
- `SIGTERM` closes the HTTP server and drains the Postgres pool for up to 10 seconds. Set `RAILWAY_DEPLOYMENT_DRAINING_SECONDS=10` on the bot service so Railway does not `SIGKILL` the process before it finishes.
- Healthcheck path: `/health` (returns `200` with `db: connected`, or `503` when the database is unreachable).
- Timezone is stored per user, auto-detected from a shared location, and defaults to `America/Chicago`.
